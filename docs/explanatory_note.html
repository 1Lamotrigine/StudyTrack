StudyTrack

Учёт учебных заданий и результатов
Пояснительная записка к индивидуальному проекту по СУБД
СУБД: PostgreSQL 16.15
Приложение: Django 5.2 (тонкая оболочка без ORM)
Запуск: Docker Compose
Данные вымышлены

1. Назначение и границы проекта

Проект реализует предметную область «учёт учебных заданий и результатов»: пользователи, категории курсов с иерархией, курсы, зачисления, задания, версии работ и оценки. Основной результат — работающая реляционная база данных PostgreSQL с ограничениями целостности, хранимой логикой, отчётами, правами доступа и воспроизводимым запуском.

Минимальное приложение на Django используется как оболочка: оно открывает соединение через psycopg, передаёт параметры отдельно от SQL-текста и вызывает созданные в БД представления и процедуры. ORM, миграции, django.contrib.auth и административная панель не используются. Все предметные расчёты выполняются SQL-объектами, а не кодом Python.

Границы: локальный запуск в Docker, консольный/веб-интерфейс без сложной аутентификации, отсутствие внешних интеграций. Выбор учебного пользователя в приложении не является проверкой личности; роль PostgreSQL и запись users различаются.

2. Модель данных и нормализация

Схема содержит восемь отношений. Центральная цепочка: courses → assignments → submission_versions → grades. Студенты связаны с курсами через enrollments (M:N), преподаватель курса хранится в courses.teacher_id, категории образуют self-FK course_categories.parent_id. История исправлений оценок вынесена в grade_history.

ОтношениеНазначениеКлючи и правила
usersСтуденты, преподаватели, администраторPK id, UQ email, CHECK role
course_categoriesИерархия категорийself-FK parent_id RESTRICT, CHECK parent_id <> id
coursesКурсыFK категории и преподавателя, UQ code
enrollmentsЗачисленияUQ (course_id, student_id), CHECK status
assignmentsЗадания, срок, max_score, JSONBCHECK max_score > 0, GENERATED-столбцы
submission_versionsВерсии работUQ (assignment_id, student_id, version_no)

Ненормализованная «ведомость» содержала списки заданий, версий и оценок в одной строке. При разложении устранены повторяющиеся группы (1НФ), частичные зависимости от составных ключей (2НФ) и транзитивные зависимости: название преподавателя, категории, курса и максимальный балл не дублируются, а получаются по FK. Для трёх основных отношений определены функциональные зависимости и кандидатные ключи:

  • users: id → ..., email → ...; ключи id, email;
  • assignments: id → ...; expected_minutes — детерминированное выражение от extra;
  • submission_versions: (assignment_id, student_id, version_no) → body, submitted_at, is_late; ключи id и эта тройка.

Дополнительные параметры задания (submission_format, expected_minutes, allow_revision) хранятся в одном JSONB-столбце. Это допустимо, потому что они не участвуют в связях и не заменяют суммы/статусы/состав документа. Числовой expected_minutes вынесен в GENERATED ALWAYS AS (...) STORED и индексирован, поэтому фильтрация выполняется по обычному столбцу.

3. Ограничения целостности и предметные операции

Правила одной строки реализованы CHECK/NOT NULL, уникальность — UNIQUE, ссылки — FK. Поведение удаления у всех предметных FK — RESTRICT: удаление справочника не должно каскадно уничтожать историю. grade_history использует SET NULL, чтобы историческая запись сохранялась после удаления оценки.

ПравилоСредство

Ключевая операция «сдача версии» реализована процедурой submit_version. Порядок блокировок фиксирован: сначала assignments, затем enrollments (SELECT ... FOR UPDATE). Под блокировкой проверяется активное зачисление, вычисляется следующий version_no и вставляется версия. Оценка и её дата записываются совместно в grade_version; при исправлении обновляется одна строка grades, а триггер пишет старую и новую оценку в grade_history. Промежуточная ошибка откатывает всю транзакцию, поэтому половина операции не сохраняется.

4. Хранимые объекты

  • VIEW v_course_results — одна строка на пару «студент — задание»: последняя версия, у которой есть оценка, с процентом и признаком просрочки. Используется отчётами и приложением.
  • VIEW v_assignment_status — одна строка на задание: число версий, сдавших студентов, просрочек, оценок и средний балл. Предварительные агрегаты в CTE исключают размножение строк при соединениях.
  • Функция fn_student_course_result(student_id, course_id) — табличная функция текущих результатов; при отсутствии записей возвращает пустой набор.
  • Процедура submit_version(...) — сдача версии с блокировкой и проверкой зачисления/разрешённых повторных сдач.
  • Процедура grade_version(...) — выставление/исправление оценки, проверка диапазона и преподавателя, запись даты.
  • Триггер trg_grades_validate — защищает правило 0 <= score <= max_score и «только преподаватель курса» даже при прямом INSERT.
  • Триггер trg_grades_history — пишет историю в другую таблицу, поэтому не вызывает рекурсивного обновления grades.

Курсорный пример sql/cursor_demo.sql открывает курсор, читает отчёт частями (FETCH 3, затем FETCH ALL) и закрывает его; рядом приведён эквивалентный обычный SELECT. Курсор полезен для построчного чтения большого отчёта, SELECT — для получения всего результата одним запросом.

5. Запросы, отчёты, окна и CTE

В sql/queries_Q01_Q16.sql собраны 16 запросов: фильтрация и сортировка, JOIN четырёх таблиц, LEFT JOIN с пустой категорией, GROUP BY/HAVING, EXISTS/NOT EXISTS, два предметных отчёта, рекурсивный CTE, ROW_NUMBER, RANK/DENSE_RANK, LAG/LEAD, NTILE(4), UNION/UNION ALL, полнотекстовый поиск, JSONB и параметризованный запрос приложения.

Условие NOT child.id = ANY(path_ids) прекращает обход при повторе узла. Проверены корень, лист и неизвестный id (пустой результат). Оконные функции применяются после группировки: ROW_NUMBER выбирает последнюю версию, RANK/DENSE_RANK строят рейтинг с равными значениями, LAG/LEAD показывают интервалы между версиями, NTILE(4) делит студентов на четыре группы по среднему проценту.

6. Полнотекстовый поиск и JSONB

Поле assignments.search_vector — GENERATED ... to_tsvector('russian', title || ' ' || description), по нему создан GIN-индекс. Поиск выполняется через websearch_to_tsquery и @@, сортировка — по ts_rank. Поддержаны слова, фраза в кавычках и исключение через минус. В отличие от LIKE, полнотекстовый поиск работает с лексемами и словоформами, а не с подстрокой; результаты могут не совпадать, и это ожидаемо.

JSONB-демонстрация показывает извлечение extra->>'submission_format', числового (extra->>'expected_minutes')::int, обновление одного ключа через jsonb_set, добавление отсутствующего ключа. Вычисляемый столбец проверен на корректном значении (45), отсутствии ключа (NULL) и неверном типе ("abc" — ошибка приведения), а также на выходе за диапазон (2 — нарушение CHECK).

7. Оптимизация, транзакции и блокировки

Для сравнения планов sql/bulk_seed_1000.sql добавляет 1000 заданий, 1000 версий и 1000 оценок (скрипт не входит в автоинициализацию). Составной индекс (course_id, due_at) обслуживает основной список заданий курса с фильтром по сроку: сначала равенство по course_id, затем диапазон и сортировка по due_at. До индекса — Seq Scan, после — Bitmap Index Scan; время запроса уменьшилось примерно с 0.21 мс до 0.06 мс. Для полнотекстового поиска GIN-индекс дал Bitmap Index Scan вместо Seq Scan (0.16 мс → 0.009 мс). Индекс по expected_minutes также используется планировщиком.

sql/transactions_demo.sql показывает BEGIN → изменение → ROLLBACK с проверкой всех связанных таблиц и отдельный успешный COMMIT. Два сеанса (sessions/session_a.sql, session_b.sql) конфликтуют за строку задания: второй ждёт освобождения и затем создаёт следующую версию без дублирования. isolation_levels_demo.sql через отдельное соединение dblink сравнивает READ COMMITTED (второе чтение видит зафиксированное изменение) и REPEATABLE READ (второе чтение сохраняет исходный снимок). deadlock_a.sql/deadlock_b.sql захватывают две строки в противоположном порядке; PostgreSQL обнаруживает взаимную блокировку и откатывает одну транзакцию. Одинаковый порядок захвата предотвращает такой сценарий.

8. Права, резервирование и приложение

Созданы роли studytrack_app (операции: SELECT/INSERT/UPDATE, без DELETE и без CREATE в схеме) и report_reader (только SELECT двух VIEW). Владелец объектов — studytrack; он может переключаться на роли для демонстрации SET ROLE. Проверено: report_reader читает v_course_results, но получает отказ на SELECT users и UPDATE courses; studytrack_app не может удалять версии и создавать таблицы.

Резервная копия снята в custom-формате (pg_dump -Fc) и восстановлена в отдельную БД studytrack_restored. Сверены 12 заданий, 48 версий, 47 оценок, 2 VIEW, 5 функций/процедур и 2 триггера; в восстановленной БД выполнена новая сдача и оценка. Команды и версии — в backup/restore_commands.md.

Django-приложение подключается через psycopg, параметры передаются отдельно от SQL-текста, соединение закрывается после запроса. Операции выполняются под SET LOCAL ROLE studytrack_app, отчёты — под report_reader; при ошибке транзакция откатывается и пользователь видит сообщение. Экран выбора учебного пользователя явно предупреждает, что это не аутентификация.

Ограничения: учебная демонстрация не является промышленной системой безопасности; user_id в приложении не доказывает личность. Отдельный механизм автоповторов при deadlock не разрабатывался — это не требуется ТЗ. Оптимизатор может выбрать Seq Scan на малых таблицах; в работе это объясняется, а не маскируется принудительным отключением.
